## 2. 하고자 하는 결과

현재 공유 중인 관리자 계정을 직원별 독립 계정으로 전환한다.

첫 대상자는 김민호 담당자와 김연희 담당자다.

각 담당자는 자신의 계정으로 로그인하고 누가 어떤 주문을 담당하는지 관리자 화면에서 확인한다.

두 담당자는 현재 단계에서 기존 `admin`과 같은 전체 관리자 접근권한을 가진다.

주문 목록에서는 미배정 주문, 내 담당 주문, 전체 주문을 쉽게 구분해서 본다.

향후 직원별로 일부 기능을 제한할 수 있는 확장 지점은 마련하지만, 세부 권한 제한 자체는 이번 1차 범위에 포함하지 않는다.

## 3. 절대 지켜야 하는 안전 원칙

- 고객의 주문 생성 과정은 변경하지 않는다.
- 결제 및 결제 콜백 과정은 변경하지 않는다.
- 고객의 주문 조회 경험은 변경하지 않는다.
- 기존 주문 398건의 값은 수정하거나 일괄 보정하지 않는다.
- `orders`와 `order_items`의 기존 컬럼 의미를 바꾸지 않는다.
- 주문 상태, 결제 상태, 공장 배정, 영업 실적 귀속 로직을 주문 담당자 기능과 결합하지 않는다.
- 기능 장애가 발생해도 주문과 결제는 계속 동작하도록 운영 기능을 격리한다.
- 새 기능을 끈 재배포로 기존 관리자 주문 화면으로 안전하게 돌아갈 수 있어야 한다.
- 공유 관리자 계정은 신규 계정의 로그인과 운영 검증이 끝나기 전까지 폐기하거나 권한을 회수하지 않는다.
- 운영 데이터에 대한 파괴적 마이그레이션, 삭제, 대규모 백필은 하지 않는다.
- 서비스 역할 키는 서버에서만 사용하고 브라우저에 노출하지 않는다.
- 계정 비밀번호, 초대 링크, 서비스 키는 저장소와 로그에 남기지 않는다.

### 4.1 운영 데이터와 계정 상태

- 2026-08-10 최초 기준선 조회에서 운영 주문 398건을 확인했다.
- 교차검토 시점의 운영 프로필은 495건이다.
- 현재 역할별 프로필 수는 `admin` 6건, `super_admin` 2건, `factory` 7건, `marketing_manager` 1건, `customer` 479건이다.
- 교차검토에서 확인한 주문 카테고리 분포는 `null` 292건, `regular` 93건, `quick` 14건이며 그 밖의 값은 0건이다.

- 주문 카테고리 분포 합계와 최초 주문 기준선은 조회 시점이 다를 수 있으므로 구현 직전에 현재 총건수를 다시 확인한다.
- **2026-08-10 15:0x KST 두 계정을 실제로 생성했다(대표 승인·비밀번호 지정).** 이 문서 최초 작성 시점의 "아직 없음" 기술은 더 이상 유효하지 않다.
- `mh@modoo.co.kr` (김민호) — `role = 'admin'`, 생성·로그인 검증 완료.
- `yh@modoo.co.kr` (김연희) — `role = 'admin'`, 생성·로그인 검증 완료.
- 검증 범위는 `createUser` → 트리거 프로필 UPDATE → `signInWithPassword` → 로그인 세션으로 자기 `profiles` 행 조회(RLS 경로) → 프로덕션 `modoo-admin-gilt.vercel.app` 브라우저 로그인 후 `/dashboard` 진입과 관리자 메뉴 노출까지다.
- 계정 생성은 담당자 기능과 독립적이므로 나머지 구현보다 먼저 수행했다. `admin_staff_members` 등록은 해당 테이블 생성 후로 남았다.
- 비밀번호는 대표가 직접 지정해 별도 채널로 전달하며 이 문서·저장소·로그에 남기지 않는다.

### 4.2 현재 인증과 권한 구조

- 로그인 정본은 Supabase Auth의 `auth.users`다.
- 애플리케이션 역할과 이름 등 서비스 프로필 정본은 `public.profiles`다.
- 관리자 화면 접근은 `profiles.role`을 읽어 판단한다.
- 현재 `admin` 역할은 재무 전용 화면을 제외한 일반 관리자 경로에 접근한다.
- 현재 `super_admin` 역할은 일반 관리자 경로와 재무 화면에 접근한다.
- 따라서 직원 로그인 계정을 별도 인증 테이블에 만들면 기존 로그인과 권한 판정 체계를 이중화하게 된다.

### 4.3 현재 주문 관련 담당 개념

현재 시스템에는 서로 다른 의미의 담당 개념이 이미 존재한다.

| 구분 | 현재 필드 또는 구조 | 의미 | 이번 기능과의 관계 |
|---|---|---|---|
| 영업담당자 | `orders.salesman_id` | 매출과 영업 실적의 귀속 | 재사용 금지 |
| 생산 공장 | `order_items.assigned_manufacturer_id` | 주문 품목의 생산처 배정 | 변경 금지 |
| 주문 처리 담당 직원 | 현재 없음 | 관리자 내부의 주문 업무 소유자 | 새로 추가 |

`orders.salesman_id`를 주문 처리 담당자로 재사용하면 매출 귀속과 내부 업무 담당이 섞인다.

`orders.id`와 `orders.parent_order_id`의 타입은 `text`다.

`orders.salesman_id`의 타입은 `uuid`이며 `profiles`가 아니라 `salesman_profiles`를 참조한다.

기존 `AssigneePicker`와 `/api/admin/assignable-staff`는 이름과 달리 영업담당자 선택 기능이므로 이번 주문 처리 담당자 기능과 분리해야 한다.

## 5. 핵심 설계 결론

### 5.1 관리자 로그인 계정은 별도 테이블로 만들지 않는다

김민호와 김연희 계정은 일반 사용자와 같은 Supabase Auth 계정으로 생성한다.

`handle_new_user()` 트리거가 만든 같은 ID의 `profiles` 행을 갱신해 `role = 'admin'`을 부여한다.

일반 회원과 같은 인증 테이블을 사용하는 것과 고객용 공개 회원가입 화면을 그대로 거치는 것은 구분해야 한다.

직원 계정은 고객용 회원가입 부수효과를 피하기 위해 서버의 Supabase Auth 관리자 API로 비밀번호를 지정해 프로비저닝한다.

인증 자격증명, 이메일, 비밀번호, 세션의 정본은 계속 `auth.users` 하나만 유지한다.

서비스 역할, 이름, 운영 속성의 정본은 계속 `profiles`와 그 확장 테이블에 둔다.

별도 관리자 계정 테이블에 이메일과 비밀번호 개념을 다시 만들지 않는다.

### 5.2 직원 운영 정보는 인증 계정과 분리한 확장 테이블에 둘 수 있다

별도 로그인 테이블은 만들지 않지만 주문 배정 대상 직원인지 여부는 별도 1대1 확장 테이블로 관리하는 방안을 권장한다.

권장 테이블명은 `admin_staff_members`다.

이 테이블은 계정을 복제하지 않고 `profiles.id`만 참조한다.

이 구조를 사용하면 기존 관리자, 대표 계정, 테스트 계정이 주문 담당자 선택 목록에 잘못 노출되는 일을 막을 수 있다.

직원 활성 상태와 주문 배정 가능 여부를 하나의 운영 상태로 관리해도 광범위하게 쓰이는 `profiles`에 운영 전용 컬럼을 추가하지 않아도 된다.

현재 이미 여러 종류의 관리자 계정이 존재하므로 주문 담당 직원 집합을 명시하는 1대1 확장 테이블이 더 명확한 선택이다.

### 5.3 주문 담당 배정은 `orders`가 아닌 별도 운영 테이블에 둔다

주문 담당자 정보는 주문의 결제나 계약 내용을 구성하지 않는 내부 운영 메타데이터다.

따라서 `orders.assignee_id` 같은 컬럼을 바로 추가하기보다 `order_staff_assignments` 테이블에 분리하는 방안을 권장한다.

이 구조에서는 담당자 기능이 실패해도 기존 주문 조회 결과와 주문 생성 경로를 그대로 유지할 수 있다.

기존 주문은 배정 행이 없으면 자동으로 미배정으로 해석하므로 백필이 필요하지 않다.

담당자 변경 이력은 별도 `order_staff_assignment_events` 테이블에 기록한다.

## 6. 제안 아키텍처

```text
Supabase Auth
  auth.users
      |
      | 같은 사용자 ID
      v
public.profiles
  role = admin
      |
      | 1:1 운영 직원 등록
      v
public.admin_staff_members
      |
      | 주문 담당 가능 직원
      v
public.order_staff_assignments -----> public.orders
      |
      | 모든 변경 이력
      v
public.order_staff_assignment_events
```

고객 주문 기능은 `orders`와 `order_items`를 기존 방식으로 계속 사용한다.

관리자 주문 화면만 별도 담당자 API를 호출해 주문 데이터와 운영 배정 데이터를 화면에서 합친다.

## 7. 계정 명세

| 이름 | 이메일 | 초기 역할 | 주문 배정 대상 | 초기 접근범위 |
|---|---|---|---|---|
| 김민호 | `mh@modoo.co.kr` | `admin` | 예 | 기존 `admin`과 동일 |
| 김연희 | `yh@modoo.co.kr` | `admin` | 예 | 기존 `admin`과 동일 |

### 7.1 계정 생성 원칙

- 이메일을 로그인 식별자로 사용한다.
- 기존 Supabase Auth 관리자 API를 통해 계정을 만든다.
- 생성 전에 Auth 사용자와 `profiles`를 모두 이메일로 조회해 중복 실행을 방지한다.
- `handle_new_user()` 트리거가 같은 사용자 ID로 만든 `profiles` 행을 INSERT하지 않고 UPDATE한다.
- 프로필 UPDATE에는 `.select(...).single()`을 사용해 0행도 실패로 검출한다.
- `profiles.name`에는 각각 `김민호`와 `김연희`를 저장한다.
- `profiles.role`에는 `admin`을 저장한다.
- `admin_staff_members`에는 두 프로필만 활성 직원으로 등록한다.
- Auth 사용자는 생성됐지만 프로필 UPDATE 또는 직원 등록이 실패하면 로그인 가능 상태로 방치하지 않고 신규 계정을 비활성화하는 보상 절차를 수행한다.
- 기존 공장 계정 생성 경로는 프로필 UPDATE 방식만 참고하고 보상 절차는 그대로 복사하지 않는다.
- **이메일 초대 방식은 사용하지 않는다 (2026-08-10 대표 결정).** 관리자 계정 생성은 드문 일이라 초대 플로우를 유지할 이유가 없다.
- 근거 보강: 이메일 초대는 이 프로젝트에서 한 번도 성공한 적이 없다 — `auth.users` 498건 중 `invited_at`이 채워진 행이 0건이다(2026-08-10 실측). 초대를 택했다면 SMTP 검증이 선행돼야 했다.
- 따라서 `adminClient.auth.admin.createUser({ email, password, email_confirm: true })`로 비밀번호를 지정해 즉시 로그인 가능한 계정을 만든다.
- 이 방식의 정확한 선례가 `app/api/admin/factory-accounts/route.ts:77-103`에 있다 — `createUser` 후 트리거가 만든 프로필을 UPDATE하는 순서를 그대로 따른다.
- 비밀번호는 강한 값을 생성해 승인된 안전한 채널로 한 번만 전달하고, 저장소·로그·이 문서에 남기지 않는다.
- 비밀번호 전달은 외부 전달에 해당하므로 별도 사람 승인을 받은 뒤 수행한다.
- 본인 비밀번호 변경은 강제하지 않되 첫 로그인 성공을 확인하기 전까지 공유 관리자 계정을 유지한다.

#### 계정 생성 실행 수단

`app/api/admin/users/route.ts`에는 `GET`과 `PATCH`만 있고 **계정 생성용 `POST`가 없다.**

즉 이 계획을 위해 관리자 계정 생성 API를 새로 만들지, 1회성 서버 실행으로 끝낼지 결정해야 한다.

관리자 계정 생성은 드문 이벤트이므로 **영구 엔드포인트와 UI를 만들지 않고 1회성 서버 사이드 실행으로 처리하는 방안을 권장한다.**

이유는 세 가지다.

- 영구 엔드포인트는 `admin` 권한자가 임의로 관리자 계정을 만들 수 있는 상시 권한 상승 표면을 새로 연다.
- 1회성 실행은 결과를 즉시 확인하고 실패 시 그 자리에서 보상할 수 있어 §7.1의 보상 절차를 코드로 유지할 필요가 없다.
- 이번 1차 범위(2명)에 UI를 만들 만한 반복성이 없다.

1회성 실행도 서비스 역할 키를 서버에서만 사용하고 사람 승인 후 수행하며 실행 기록을 남긴다.

## 8. 제안 데이터 모델

### 8.1 `admin_staff_members` — ⛔ v3에서 폐기

**이 테이블은 만들지 않는다. §25의 범위 축소로 존재 이유가 사라졌다.**

이 테이블의 유일한 목적은 "담당자 선택 목록에 누구를 띄울까"였다.

v3에서는 **본인만 자신에게 배정**하므로 선택 목록 자체가 없다.

아래 설계는 남에게 배정하는 기능이 필요해질 때를 대비해 기록으로만 남긴다.

| 컬럼 | 타입 | 제약과 의미 |
|---|---|---|
| `profile_id` | `uuid` | 기본키이며 `profiles.id` 참조 |
| `is_active` | `boolean` | 기본값 `true`이며 활성 직원이자 주문 배정 대상인지 표시 |
| `created_at` | `timestamptz` | 생성 시각 |
| `updated_at` | `timestamptz` | 마지막 변경 시각 |

이메일, 비밀번호, 역할, 이름은 이 테이블에 중복 저장하지 않는다.

### 8.2 `order_staff_assignments`

이 테이블은 주문별 현재 담당자 한 명을 표현한다.

| 컬럼 | 타입 | 제약과 의미 |
|---|---|---|
| `order_id` | `text` | 기본키이며 `orders.id`와 같은 타입으로 주문당 현재 배정 한 건 보장 |
| `assignee_profile_id` | `uuid nullable` | 현재 담당자의 `profiles.id` 참조 |
| `assigned_by_profile_id` | `uuid nullable` | 마지막 변경을 수행한 관리자의 `profiles.id` 참조 |
| `assigned_at` | `timestamptz nullable` | 현재 담당자가 배정된 시각 |
| `updated_at` | `timestamptz` | 마지막 변경 시각 |
| `version` | `bigint` | 낙관적 잠금에 사용하는 증가 버전 |

`order_id` 외래키는 `ON DELETE CASCADE`로 설정해 실제 존재하는 슈퍼관리자 주문 삭제 경로를 막지 않아야 한다.

현재 배정 테이블의 담당자와 실행자 프로필 외래키에는 `ON DELETE SET NULL`을 사용해 계정 정리가 주문 삭제를 막지 않게 한다.

담당자를 해제한 주문은 행을 삭제하지 않고 `assignee_profile_id = null`로 갱신하는 방안을 권장한다.

기존 주문에 배정 행이 없거나 담당자 값이 `null`이면 모두 미배정으로 해석한다.

일반 배정, 재배정, 해제는 요청의 `expected_version`과 현재 `version`이 일치할 때만 성공한다.

배정 행이 없는 주문은 초기 버전 `0`으로 해석한다.

`claim`은 배정 행 없음과 `assignee_profile_id = null`인 기존 행을 하나의 원자적 UPSERT에서 처리한다.

`claim`의 전제조건은 `expected = 'unassigned'`이며 현재 담당자가 있으면 변경하지 않고 최신 담당자와 버전을 반환한다.

`assignee_profile_id`와 `updated_at`에는 조회용 인덱스를 둔다.

### 8.3 `order_staff_assignment_events`

이 테이블은 담당자 배정, 변경, 해제의 감사 이력을 보존한다.

| 컬럼 | 타입 | 제약과 의미 |
|---|---|---|
| `id` | `uuid` | 기본키 |
| `order_id` | `text` | 외래키 없이 보존하는 변경 대상 주문 ID |
| `previous_assignee_profile_id` | `uuid nullable` | 외래키 없이 보존하는 변경 전 담당자 ID |
| `next_assignee_profile_id` | `uuid nullable` | 외래키 없이 보존하는 변경 후 담당자 ID |
| `actor_profile_id` | `uuid` | 외래키 없이 보존하는 변경 실행자 ID |
| `previous_assignee_name_snapshot` | `text nullable` | 변경 전 담당자 이름 스냅샷 |
| `next_assignee_name_snapshot` | `text nullable` | 변경 후 담당자 이름 스냅샷 |
| `actor_name_snapshot` | `text` | 변경 실행자 이름 스냅샷 |
| `action` | 제한된 문자열 | `assign`, `reassign`, `unassign`, `claim` 중 하나 |
| `created_at` | `timestamptz` | 변경 시각 |

이력 테이블의 주문 ID와 세 프로필 ID에는 외래키를 두지 않는다.

세 ID와 세 이름 스냅샷을 이벤트 자체에 보존해 주문이나 계정 삭제 후에도 재배정 전후와 실행자를 식별할 수 있게 한다.

## 9. 기능 명세

### 9.1 주문 목록 범위

| 보기 | 포함 조건 | 목적 |
|---|---|---|
| 업무함 | 미배정 진행 주문과 내 담당 진행 주문 | 기본 업무 화면 |
| 내 담당 | 로그인한 직원에게 배정된 주문 | 개인 업무 집중 |
| 미배정 | 담당자가 없고 아직 종료되지 않은 주문 | 신규 주문 배정 |
| 전체 | 기존과 같은 전체 주문 | 검색, 감독, 과거 주문 확인 |

기본 진입 보기는 `업무함`을 권장한다.

`delivered`, `cancelled`, `partially_cancelled` 주문은 업무함과 미배정 카운트에서 제외하는 방안을 권장한다.

업무함과 미배정에서 독립 주문으로 취급하는 조건은 `parent_order_id IS NULL`이다.

`parent_order_id IS NOT NULL`인 자식 주문은 독립 미배정 주문으로 쌓지 않고 부모 주문 아래에서 표시한다.

자식 주문에는 별도 배정 행을 만들지 않고 조회 시점에 부모 주문의 담당자를 따른다.

`order_category`는 운영 주문의 다수가 `null`이므로 신규 조건은 반드시 NULL-safe하게 작성한다.

`order_category != 'surcharge'`처럼 `null` 행을 탈락시키는 조건은 사용하지 않는다.

종료 주문은 전체 보기와 검색 결과에서는 계속 확인할 수 있어야 한다.

담당자별 필터에는 활성 주문 담당 직원과 `미배정` 항목을 제공한다.

### 9.2 주문 담당자 표시

- 주문 목록 행에 현재 담당자 이름 또는 `미배정` 배지를 표시한다.
- 주문 상세 화면에 현재 담당자와 마지막 배정 시각을 표시한다.
- 주문 상세 화면에서 담당자를 선택, 변경, 해제할 수 있게 한다.
- 담당자 이름은 `profiles.name`을 기준으로 표시한다.
- 비활성화된 과거 담당자는 현재 배정과 이력에서 식별 가능해야 하지만 신규 선택 목록에서는 제외한다.

### 9.3 배정 동작

- 현재 단계에서는 `admin`과 `super_admin`이 활성 직원에게 주문을 배정할 수 있다.
- 현재 단계에서는 `admin`과 `super_admin`이 담당자를 변경하거나 해제할 수 있다.
- 미배정 주문을 자신에게 가져오는 `내가 맡기` 동작을 제공할 수 있다.
- `claim`은 일반 배정과 같은 API 경로를 사용하되 `expected = 'unassigned'`라는 별도 원자적 전이로 처리한다.
- 모든 배정 변경에는 실행자, 변경 전 담당자, 변경 후 담당자, 시각을 기록한다.
- 동시에 같은 미배정 주문을 가져오면 한 명만 성공해야 한다.
- 경쟁에서 늦은 요청은 `409 Conflict`와 현재 담당자 정보를 받아야 한다.
- 담당자 변경은 주문 금액, 주문 상태, 결제 상태, 고객 정보, 영업담당자, 공장 배정 값을 수정하지 않아야 한다.

### 9.4 접근 범위

- 김민호와 김연희는 1차 출시에서 전체 주문을 볼 수 있다.
- `내 담당`과 `미배정`은 접근 제한이 아니라 업무용 필터다.
- 자신의 담당이 아닌 주문도 `전체`에서 확인할 수 있다.
- 1차 출시에서는 기존 `admin`이 접근하던 메뉴를 별도로 제한하지 않는다.
- 담당자 API는 `admin`과 `super_admin`만 허용하고 `factory`에는 `403 Forbidden`을 반환한다.
- 공장 계정의 주문 화면에는 담당자 컬럼, 필터, 배정 버튼을 렌더하지 않는다.
- 담당자 UI는 전역 기능 플래그가 켜지고 로그인 사용자가 활성 `admin_staff_members`이거나 `super_admin`일 때만 표시한다.

## 10. 향후 세부 권한 확장 방향

향후 일부 기능을 제한해야 해도 로그인 계정 테이블을 새로 만들 필요는 없다.

`profiles.role`은 큰 역할 구분에 계속 사용한다.

세부 기능은 `admin_permission_overrides` 같은 별도 기능 권한 테이블로 확장할 수 있다.

예시 권한 키는 `orders.view_all`, `orders.assign`, `orders.reassign`, `orders.update_status`, `finance.view`가 될 수 있다.

기본 권한은 역할에서 결정하고 직원별 예외만 별도 테이블에 저장하는 방식을 권장한다.

이 방식은 지금의 전체 권한을 유지하면서 나중에 필요한 기능만 제한할 수 있다.

세부 권한 시스템의 실제 구현은 1차 출시 범위에 포함하지 않는다.

## 11. API와 서버 처리 계획

### 11.1 제안 API

| 메서드와 경로 | 역할 | v3 |
|---|---|---|
| ~~`GET /api/admin/order-assignees`~~ | 배정 가능한 직원 목록 조회 | ⛔ 폐기 — 본인만 배정하므로 목록이 없다 |
| `POST /api/admin/order-assignments/batch` | 요청 본문의 `order_ids`에 해당하는 현재 담당자 일괄 조회 | 유지 |
| `PUT /api/admin/order-assignments/[orderId]` | claim(본인 배정)과 release(본인 해제) 수행 | 유지, 동작 축소 |

경로 이름과 메서드는 구현 전에 기존 API 규칙에 맞춰 조정할 수 있다.

### 11.2 서버 보안 규칙

- 모든 엔드포인트는 현재 로그인 세션을 검증한다.
- `ORDER_ASSIGNMENT_ENABLED`가 비활성이면 담당자 API는 기능 비활성 응답을 반환하고 데이터를 읽거나 쓰지 않는다.
- 실행자 ID는 요청 본문에서 신뢰하지 않고 로그인 세션에서 파생한다.
- 실행자의 `profiles.role`이 `isAdminLike`를 통과하는지 서버에서 다시 확인한다.
- `factory` 역할은 담당자 API 전체에서 `403 Forbidden`으로 차단한다.
- 대상 담당자가 활성 `admin_staff_members`인지 서버에서 확인한다.
- 브라우저가 서비스 역할 키로 테이블을 직접 읽거나 쓰게 하지 않는다.
- 신규 테이블은 RLS를 활성화하고 브라우저 직접 접근 정책은 기본적으로 열지 않는다.
- 서버 API만 서비스 역할 클라이언트를 사용한다.
- 요청 본문은 허용 필드만 스키마 검증한다.
- 사용자별 UI 개방 조건은 API 역할 권한과 구분하며 일반 관리자가 직접 API를 호출해도 기존 관리자 권한을 넘지 않는다.

### 11.3 동시성 및 감사 일관성

현재 배정 변경과 이력 추가는 하나의 데이터베이스 트랜잭션으로 처리해야 한다.

Supabase API에서 두 작업을 따로 실행하면 배정은 바뀌었지만 이력은 빠지는 중간 실패가 생길 수 있다.

원자적 데이터베이스 함수 또는 같은 수준의 트랜잭션 경계를 사용한다.

`version` 조건을 사용해 늦게 도착한 화면이 최신 배정을 덮어쓰지 못하게 한다.

서버는 세션과 역할을 검증한 뒤 `createAdminClient().rpc(...)`로 원자적 데이터베이스 함수를 호출한다.

신규 함수는 기본 `SECURITY INVOKER`를 사용하고 `SET search_path = public, pg_temp`를 명시한다.

신규 함수는 `REVOKE ALL ON FUNCTION ... FROM PUBLIC` 후 `GRANT EXECUTE ON FUNCTION ... TO service_role`만 부여한다.

배정 행 없음과 담당자 값이 `null`인 행은 원자적 함수 내부에서 모두 처리한다.

조건 충돌은 최신 담당자와 버전을 포함한 `409 Conflict`로 반환한다.

## 12. 기존 주문 API와 화면의 변경 원칙

기존 `/api/admin/orders`의 주문 조회와 수정 동작은 1차 단계에서 그대로 유지한다.

주문 목록 화면은 기존 주문 조회 성공 후 주문 ID 배열을 요청 본문에 담아 담당자 batch 조회를 별도로 수행한다.

담당자 조회가 실패하면 주문 목록은 기존 방식으로 표시하고 담당자 영역만 `불러오기 실패` 상태로 처리한다.

담당자 조회 실패를 미배정으로 해석하지 않는다.

담당자 상태를 알 수 없으면 `업무함`, `내 담당`, `미배정` 필터와 배정 변경 동작을 비활성화한다.

담당자 기능 오류 때문에 주문 목록 전체가 빈 화면이 되어서는 안 된다.

기존 영업담당자 선택 컴포넌트는 역할이 드러나는 이름으로 정리하고 신규 주문 담당자 컴포넌트와 혼용하지 않는다.

기존 주문 타입에는 화면 조합용 선택 필드만 추가하고 데이터베이스의 기존 필드 의미는 변경하지 않는다.

## 13. 구현 계획

### 단계 0: 구현 전 기준선 고정

- 운영 코드와 데이터베이스 스키마의 최신 상태를 다시 읽는다.
- 현재 주문 생성, 결제, 고객 주문 조회, 관리자 주문 조회의 기준 동작을 기록한다.
- 테스트용 주문과 테스트용 관리자 계정을 운영 데이터와 구분해 준비한다.
- 기존 미커밋 변경과 이번 작업을 분리한다.
- 전역 기능 플래그는 기본값이 비활성인 서버 환경변수 `ORDER_ASSIGNMENT_ENABLED` 하나로 정한다.

### 단계 1: 추가형 데이터베이스 마이그레이션 작성

- `admin_staff_members`를 새로 만든다.
- `order_staff_assignments`를 새로 만든다.
- `order_staff_assignment_events`를 새로 만든다.
- 필요한 인덱스와 제약을 추가한다.
- 신규 테이블의 RLS를 활성화한다.
- 계정 삭제와 주문 삭제 시 각 외래키 동작을 별도로 검증한다.
- 기존 테이블의 컬럼, 값, 정책, 트리거는 변경하지 않는다.
- 기존 주문에 대한 백필은 수행하지 않는다.
- 마이그레이션의 적용과 되돌림 절차를 문서화한다.

### 단계 2: 서버 API 구현

- 관리자 세션과 역할 검증을 공통화한다.
- 배정 가능한 직원 조회 API를 구현한다.
- 주문별 담당자 일괄 조회 API를 구현한다.
- 배정, 재배정, 해제 API를 구현한다.
- `내가 맡기`의 경쟁 조건을 원자적으로 처리한다.
- 모든 변경을 감사 이벤트에 기록한다.
- 담당자 API 장애가 주문 API로 전파되지 않게 한다.

### 단계 3: 관리자 화면 구현

- 주문 목록에 `업무함`, `내 담당`, `미배정`, `전체` 보기를 추가한다.
- 주문 행과 상세 화면에 담당자 배지를 추가한다.
- 담당자 선택, 변경, 해제 UI를 추가한다.
- 담당자 조회 실패와 변경 충돌을 사용자에게 명확히 안내한다.
- 기능 플래그가 꺼지면 기존 주문 화면과 같은 동작을 유지한다.
- 활성 `admin_staff_members`와 `super_admin`에게만 담당자 UI를 표시한다.
- `factory`에는 담당자 UI를 렌더하지 않는다.
- 기존 영업담당자 UI와 신규 주문 담당자 UI의 명칭을 명확히 구분한다.

### 단계 4: 자동 테스트와 수동 회귀 검증

- 필터 계산과 종료 상태 제외 규칙을 단위 테스트한다.
- 인증 실패, 권한 실패, 잘못된 담당자, 존재하지 않는 주문을 API 테스트한다.
- 계정 생성 요청을 재실행해도 중복 Auth 사용자나 중복 직원 행이 생기지 않는지 테스트한다.
- 프로필 생성이 실패한 경우 신규 Auth 사용자가 활성 상태로 남지 않는지 테스트한다.
- 프로필 UPDATE가 0행이면 `.single()`이 실패로 처리하고 보상 절차가 실행되는지 테스트한다.
- 배정 행 없음과 담당자 값이 `null`인 두 claim 분기에서 한 요청만 성공하고 다른 요청이 `409`를 받는지 테스트한다.
- 배정 변경과 감사 이벤트가 함께 성공하거나 함께 실패하는지 테스트한다.
- 담당자 API를 강제로 실패시켜도 기존 주문 목록이 표시되는지 테스트한다.
- 담당자 batch 조회 실패 시 모든 주문이 미배정으로 표시되지 않고 담당자 기반 필터와 변경 동작이 비활성화되는지 테스트한다.
- 전체 주문 ID를 batch 요청 본문으로 보내고 URL 쿼리스트링에 `order_ids`가 포함되지 않는지 테스트한다.
- `order_category = null`인 루트 주문이 업무함에 포함되는지 테스트한다.
- `parent_order_id IS NOT NULL`인 자식 주문이 독립 미배정 건수에서 제외되고 부모 담당자를 따르는지 테스트한다.
- 공장 계정이 담당자 API에서 `403`을 받고 주문 화면에서 담당자 UI를 보지 못하는지 테스트한다.
- 신규 RPC를 `anon`, `authenticated`, `PUBLIC`이 실행하지 못하고 `service_role`만 실행할 수 있는지 테스트한다.
- 프로필을 삭제해도 감사 이벤트의 세 ID와 재배정 전후 및 실행자 이름 스냅샷이 보존되는지 테스트한다.
- 고객 회원가입, 로그인, 견적 또는 주문 생성, 결제 샌드박스, 주문 조회를 회귀 테스트한다.
- 관리자 주문 상태 변경과 공장 배정이 기존대로 동작하는지 테스트한다.
- `salesman_id`와 영업 실적 화면이 변하지 않았는지 테스트한다.
- 두 개의 독립 브라우저 세션으로 김민호와 김연희의 동시 사용을 검증한다.

### 단계 5: 운영 반영과 계정 생성

- 트래픽이 낮은 시간에 추가형 마이그레이션을 적용한다.
- 기능 플래그를 끈 상태로 애플리케이션을 배포한다.
- 기존 고객 주문과 관리자 주문 화면의 운영 스모크 테스트를 먼저 수행한다.
- 김민호와 김연희의 Auth 계정을 만들고 트리거가 만든 `profiles`를 관리자 정보로 갱신한다.
- 두 프로필을 `admin_staff_members`에 등록한다.
- 각 담당자의 독립 로그인과 전체 관리자 접근을 확인한다.
- 전역 기능 플래그를 활성화한 배포에서 두 활성 직원과 `super_admin`에게만 담당자 UI가 표시되는지 확인한다.
- 이상이 없으면 두 담당자가 실제 업무를 시작하도록 사람 승인을 받는다.
- 초기 운영 기간에는 오류 로그, 담당자 API 실패율, 주문 목록 로딩 실패를 집중 관찰한다.

### 단계 6: 공유 계정 정리

- 두 직원이 독립 계정으로 정상 업무를 수행하는지 확인한다.
- 공유 계정이 자동화나 외부 연동에 사용되는지 다시 확인한다.
- 사람 승인을 받은 뒤 공유 계정의 비밀번호 변경, 비활성화, 역할 축소 중 적절한 조치를 수행한다.
- 공유 계정 정리는 신규 기능 배포와 같은 작업으로 묶지 않는다.

## 14. 배포와 롤백 계획

### 14.1 배포 원칙

- 데이터베이스 변경은 신규 테이블 추가만 허용한다.
- 애플리케이션 변경은 기능 플래그 뒤에 둔다.
- `ORDER_ASSIGNMENT_ENABLED` 변경은 재배포 후 적용된다는 점을 운영 절차에 명시한다.
- 운영 계정 생성은 코드와 마이그레이션 검증 후에 수행한다.
- 고객 주문 플로우의 정상 여부를 계정 개방보다 먼저 확인한다.
- 운영 중 실제 고객 주문을 테스트 대상으로 수정하지 않는다.

### 14.2 장애 시 롤백

- 첫 조치는 `ORDER_ASSIGNMENT_ENABLED`를 끈 배포로 담당자 UI와 API 사용을 중단하는 것이다.
- 기존 주문 API와 기존 주문 화면은 계속 사용한다.
- 신규 테이블은 주문 핵심 데이터에 영향을 주지 않으므로 긴급 삭제하지 않는다.
- 계정 자체에 문제가 있으면 신규 직원 계정만 비활성화하고 공유 계정으로 복귀한다.
- 주문 또는 결제 회귀가 의심되면 신규 UI와 API 배포만 되돌리고 데이터베이스 테이블은 보존한다.
- 롤백 과정에서도 기존 주문 데이터는 수정하거나 삭제하지 않는다.

## 17. 대안 검토

### 대안 A: 별도 관리자 계정 테이블에 로그인 정보를 저장한다

이 대안은 권장하지 않는다.

Supabase Auth와 별도 계정 테이블 사이에 이메일, 비밀번호, 활성 상태, 탈퇴 상태를 동기화해야 한다.

기존 관리자 접근 검사가 `profiles.role`을 사용하므로 인증 경로를 크게 다시 만들어야 한다.

동기화 실패가 로그인 장애나 권한 불일치로 이어질 수 있다.

### 대안 B: 일반 계정에 `admin` 역할만 부여하고 추가 직원 테이블은 만들지 않는다

이 대안은 가장 단순하고 두 명만 운영할 때는 충분히 동작한다.

하지만 기존 관리자, 대표 계정, 테스트 계정까지 주문 담당자 목록에 섞일 수 있다.

`profiles`에 운영 전용 불리언과 권한 컬럼이 계속 늘어날 가능성이 있다.

따라서 로그인 정본은 그대로 두되 `admin_staff_members`를 얇은 확장 테이블로 두는 방안을 더 권장한다.

### 대안 C: `orders.assignee_profile_id` 컬럼을 직접 추가한다

이 대안은 조회가 단순하고 조인 수가 적다.

하지만 매출 핵심 테이블의 스키마와 기존 주문 API를 직접 건드리게 된다.

담당자 기능 장애를 주문 도메인에서 분리하기 어렵고 회귀 영향 범위가 커진다.

현재 안전 우선 조건에서는 별도 운영 테이블이 더 적절하다.

### 대안 D: 기존 `orders.salesman_id`를 재사용한다

이 대안은 절대 권장하지 않는다.

영업 실적 귀속과 주문 처리 업무 담당은 서로 다른 개념이다.

재사용하면 영업 통계와 파트너몰 귀속이 오염될 수 있다.

### 대안 E: 브라우저 로컬 상태나 메모에만 담당자를 저장한다

이 대안은 여러 직원과 기기 사이에서 동기화되지 않는다.

감사 이력과 동시성 제어가 불가능하다.

운영 주문 관리 기능으로 사용할 수 없다.

## 18. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 기존 모든 관리자 계정이 담당자 선택 목록에 노출 | 잘못된 배정 | `admin_staff_members`로 명시적 대상만 등록 |
| Auth 생성 후 프로필 UPDATE 실패 | 로그인 가능한 불완전 계정 잔존 | `.single()` 검증과 신규 Auth 사용자 비활성화 |

## 22. 최종 제안 요약

직원 로그인 계정은 별도 테이블에 복제하지 않고 기존 Supabase Auth와 `profiles`를 사용한다.

주문 담당 대상 직원이라는 운영 속성만 `admin_staff_members`에 분리한다.

주문 담당 배정과 이력은 `orders`에서 분리한 신규 운영 테이블에 저장한다.

현재 배정은 주문 삭제를 따르지만 감사 이벤트의 주문과 사용자 ID 및 이름 스냅샷은 외래키 없이 보존한다.

김민호와 김연희는 1차 출시에서 `admin` 전체 권한을 가진다.

`업무함`, `내 담당`, `미배정`, `전체`는 권한 제한이 아니라 업무 필터로 제공한다.

자식 주문은 독립 미배정으로 집계하지 않고 조회 시점에 부모 주문의 담당자를 따른다.

담당자 API는 `admin`과 `super_admin`만 사용하고 공장 계정에는 UI를 노출하지 않는다.

담당자 UI는 전역 기능 플래그가 켜진 활성 직원과 `super_admin`에게만 노출한다.

배정 변경은 서비스 역할 전용 RPC에서 현재 배정과 감사 이벤트를 원자적으로 기록한다.

고객 주문과 결제 경로를 건드리지 않는 추가형 구조, 기능 플래그, 무백필 배포, 별도 롤백 경로를 필수 조건으로 삼는다.

다른 세션의 설계 검토와 사람의 구현 승인이 끝나기 전에는 계정 생성, 데이터베이스 마이그레이션, 코드 변경을 시작하지 않는다.

## 24. 관리자 접속 로그 (2026-08-10 대표 지시)

### 24.1 요구사항

관리자 계정의 접속 기록을 남겨 누가 언제 어디서 접속했는지 사후에 확인할 수 있어야 한다.

IP 차단이나 접속 제한은 이번 범위가 아니다. 기록과 조회만 한다.

### 24.2 현재 상태 실측 (2026-08-10)

| 확인 대상 | 결과 | 판정 |
|---|---|---|
| `auth.audit_log_entries` | **0건**. Supabase 자체 감사 로그가 이 프로젝트에 남지 않는다 | 사용 불가 |
| `auth.sessions` | 667건, 419명, 2026-01-09부터 누적. `ip`·`user_agent`·`created_at` 보유 | 데이터는 있으나 감사 로그 아님 |
| 세션 영속성 | **로그아웃하면 행이 삭제된다.** 검증 중 생성한 로그인 세션이 로그아웃 직후 사라진 것을 확인했다 | 감사 추적으로 사용 불가 |

결론은 이렇다.

플랫폼이 로그인 시점에 IP와 User-Agent를 이미 수집하고 있으므로 **새로 수집할 필요는 없고, 사라지기 전에 복사해 보존하면 된다.**

### 24.3 권장 구조

`auth.sessions`에 `AFTER INSERT` 트리거를 걸어 관리자 계정의 세션 생성 시 `public.admin_access_logs`에 한 행을 복사한다.

이 방식의 장점은 세 가지다.

- **로그인 경로 코드를 전혀 건드리지 않는다.** 운영 중인 로그인에 회귀 위험을 만들지 않는다.
- 앱을 거치지 않은 로그인(직접 API 호출 등)도 빠짐없이 잡힌다.
- IP와 User-Agent를 클라이언트가 아니라 플랫폼이 기록한 값으로 확보한다. 클라이언트 신고값은 위조 가능하므로 쓰지 않는다.

이 프로젝트에는 이미 `auth` 스키마 트리거 선례가 있다 — `auth.users`의 `on_auth_user_created`.

### 24.4 `admin_access_logs`

| 컬럼 | 타입 | 의미 |
|---|---|---|
| `id` | `uuid` | 기본키 |
| `profile_id` | `uuid` | 외래키 없이 보존하는 접속자 ID |
| `email_snapshot` | `text` | 접속 시점 이메일 |
| `name_snapshot` | `text nullable` | 접속 시점 이름 |
| `role_snapshot` | `text` | 접속 시점 역할 |
| `event` | 제한된 문자열 | 1차는 `login`만. 확장 시 `logout`, `login_failed` |
| `ip` | `inet nullable` | `auth.sessions.ip` 복사 |
| `user_agent` | `text nullable` | `auth.sessions.user_agent` 복사 |
| `session_id` | `uuid nullable` | 원본 세션 ID(중복 방지용, unique) |
| `created_at` | `timestamptz` | 접속 시각 |

스냅샷을 쓰는 이유는 §8.3과 같다 — 계정이 삭제·변경돼도 당시 기록이 읽혀야 한다.

`session_id`에 unique 제약을 두어 트리거 재실행 시 중복 적재를 막는다.

`created_at`과 `profile_id`에 조회용 인덱스를 둔다.

### 24.5 안전 규칙

- 트리거 함수는 `handle_new_user()`와 같이 **예외를 삼켜야 한다.** 로그 적재 실패가 로그인을 막아서는 안 된다. 다만 `RAISE WARNING`으로 흔적은 남긴다.
- 관리자 역할(`admin`, `super_admin`)만 적재한다. 고객 로그인까지 담으면 테이블이 무의미하게 커진다.
- 테이블은 RLS를 활성화하고 브라우저 직접 접근 정책을 열지 않는다. 조회는 서버 API로만 한다.
- 조회 권한은 `super_admin`으로 제한한다. 일반 `admin`이 동료의 접속 IP를 열람할 이유가 없다.
- 비밀번호·토큰·세션 토큰은 어떤 형태로도 저장하지 않는다.
- 보존 기간을 정하고(권장 1년) 초과분 정리 방침을 문서화한다. 개인정보에 해당하는 IP를 무기한 보관하지 않는다.

### 24.6 알려진 한계 — 실패한 로그인은 잡히지 않는다

세션이 만들어지지 않으므로 **비밀번호 오류 등 실패한 로그인 시도는 이 방식으로 기록되지 않는다.**

실패까지 남기려면 로그인을 클라이언트 `signInWithPassword`가 아니라 서버 라우트로 우회시켜야 하고, 그것은 운영 중인 로그인 경로를 바꾸는 일이라 회귀 위험이 있다.

따라서 1차는 **성공 로그인 기록까지만** 하고, 실패 시도 기록은 별도 작업으로 분리한다.

무차별 대입 탐지가 필요해지는 시점에 다시 판단한다.

### 24.7 추가 주의 — `auth` 스키마 트리거의 취약성

`auth` 스키마 객체는 Supabase 플랫폼 업그레이드나 프로젝트 복원 과정에서 유실될 수 있다.

트리거가 조용히 사라지면 로그가 끊기는데 아무도 모른다.

따라서 **"최근 N일간 관리자 로그인 기록이 0건이면 경보"** 를 자동화 감시 대상에 넣는다.

이는 감지 채널 자체를 감시 대상으로 삼는 기존 운영 원칙과 같은 맥락이다.

### 24.8 이번 계획과의 관계

관리자 접속 로그는 주문 담당자 기능과 **독립적이다.**

`admin_staff_members`나 `order_staff_assignments`에 의존하지 않으므로 담당자 기능보다 먼저 배포해도 되고, 별도로 롤백해도 된다.

기능 플래그도 공유하지 않는다.

## 25. 확정 범위 v3 (2026-08-10 대표 지시) — 앞 섹션보다 우선한다

### 25.1 대표가 지정한 필요 기능

- 두 담당자는 모든 주문을 볼 수 있다.
- 두 담당자는 **본인을 담당자로 배치**할 수 있다.
- 두 담당자는 **본인이 담당하는 주문만 보는 필터**를 쓸 수 있다.

이 세 가지면 충분하다.

### 25.2 이 범위가 제거하는 것

| 제거 대상 | 이유 |
|---|---|
| `admin_staff_members` 테이블 | 담당자 선택 목록이 없어졌다. 배정 대상은 항상 "로그인한 본인"이다 |
| `GET /api/admin/order-assignees` | 위와 같은 이유 |
| 남에게 배정·재배정 UI | 범위 밖 |
| 담당자별 드롭다운 필터 | 필요해지면 `order_staff_assignments`의 distinct 담당자로 목록을 만들 수 있어 테이블이 필요 없다 |
| 기능 플래그를 직원 등록 여부와 연동하는 규칙(§13) | 등록 테이블이 없다. 전역 `ORDER_ASSIGNMENT_ENABLED` 하나만 남는다 |

테이블 3개 → **2개**, API 3개 → **2개**로 줄어든다.

### 25.3 이 범위에서도 반드시 남겨야 하는 것

- `order_staff_assignments` — 주문당 현재 담당자 1명, `version` 낙관적 잠금.
- **claim의 원자성** — 두 명이 같은 주문을 동시에 집으면 한 명만 성공하고 다른 쪽은 `409`를 받아야 한다. 담당자가 두 명이므로 이 경합은 실제로 발생한다.
- **release(본인 해제)** — 대표 지시에 없지만 실무상 필수다. 잘못 집었을 때 놓을 방법이 없으면 그 주문은 영원히 그 사람 것이 된다. 본인 것만 해제할 수 있게 한다.
- `order_staff_assignment_events` — 유지한다. 대표가 관리자 접속 로그(§24)를 요구한 것과 같은 맥락에서 "누가 언제 어떤 주문을 맡고 놓았는지"의 추적 가치가 있고 비용이 낮다.
- 담당자 batch 조회 실패를 미배정으로 해석하지 않는 규칙(§12).
- 공장 계정 차단과 UI 비노출(§9.4).
- `parent_order_id IS NULL` 기준과 NULL-safe 카테고리 조건(§9.1).

### 25.4 주문 목록 보기 (v3 확정)

| 보기 | 조건 | 비고 |
|---|---|---|
| 전체 | 기존과 동일 | 기본 진입 |
| 내 담당 | `assignee_profile_id = 로그인 사용자` | 대표 지시 항목 |
| 미배정 | 배정 행 없음 또는 `assignee_profile_id IS NULL`, 그리고 `parent_order_id IS NULL` | 집을 주문을 찾으려면 사실상 필요하다. 데이터가 이미 있어 클라이언트 필터로 무료다 |

§9.1의 `업무함`은 폐기한다. 전체·내 담당·미배정 세 개면 충분하고 기본 진입은 기존과 같은 `전체`로 둔다.

기본 진입을 바꾸지 않으면 기존 관리자들의 화면 경험이 그대로 유지된다.

### 25.5 남은 판단 — 자리 비움 시 재배정

대표 지시에는 남에게 배정하는 기능이 없다.

그런데 담당자가 휴가·병가로 자리를 비우면 그 사람이 잡은 주문을 아무도 처리할 수 없게 된다.

가장 작은 대비책으로 **`super_admin`에 한해 타인 배정 해제를 허용**하는 것을 권장한다.

`super_admin`은 이미 주문 삭제 권한까지 가지고 있어 새로운 권한 상승이 아니다.

이 항목은 대표 확인이 필요하다.

### 25.6 v3 기준 완료 조건

- 김연희와 김민호가 각자 계정으로 로그인해 전체 주문을 본다. (계정은 §4.1로 이미 완료)
- 미배정 주문에서 `내가 맡기`를 눌러 본인 담당으로 만든다.
- `내 담당` 필터에서 본인이 맡은 주문만 보인다.
- 두 사람이 같은 주문을 동시에 맡으면 한 명만 성공하고 다른 한 명은 최신 담당자와 함께 `409`를 받는다.
- 본인이 맡은 주문을 해제하면 다시 미배정으로 돌아간다.
- 담당자 API가 죽어도 기존 주문 목록과 고객 주문·결제는 정상 동작한다.
- `orders`의 금액·상태·결제·영업담당자·공장 배정 값이 변하지 않는다.

## 26. 확정 범위 v3.1 (2026-08-10) — §25를 보정한다

### 26.1 변경 이유

대표가 `super_admin`은 본인 배정 외에 **타인에게 직접 배정**할 수 있어야 한다고 확정했다.

그 순간 "배정 가능한 사람 목록"이 다시 필요해지므로, §25.2에서 폐기했던 배정 대상 관리를 되살린다.

§25에서 이를 폐기한 것은 "본인만 배정"이라는 전제에 의존한 판단이었고 그 전제가 바뀌었다.

### 26.2 목록이 필요한 실측 근거

2026-08-10 기준 `role IN ('admin','super_admin')` 계정은 **10개**다.

### 26.3 저장 방식 — 테이블 대신 컬럼 하나

`admin_staff_members` 테이블을 되살리지 않고 **`profiles.can_receive_orders boolean NOT NULL DEFAULT false`** 한 컬럼으로 처리한다.

| 항목 | 테이블 방식 | 컬럼 방식 (채택) |
|---|---|---|
| 마이그레이션 | 테이블 + FK + RLS + 인덱스 | `ALTER TABLE ... ADD COLUMN` 한 줄 |
| 신규 테이블 수 | 3개 | **2개 유지** |
| 표현하는 것 | 배정 자격 + 활성 상태 + 생성/변경 시각 | 배정 자격 한 가지 |

v3.1 범위에는 세부 권한 확장이 없어 테이블이 담을 추가 속성이 없다.

운영 전용 속성이 더 필요해지면 그때 테이블로 승격한다.

초기값은 `mh@modoo.co.kr`와 `yh@modoo.co.kr` 두 계정만 `true`로 설정하고 나머지는 기본값 `false`로 둔다.

### 26.4 권한 매트릭스 (확정)

| 동작 | `admin` | `super_admin` | `factory` |
|---|---|---|---|
| 전체 주문 조회 | ✅ | ✅ | 기존과 동일(자기 공장분) |
| 본인에게 배정(claim) | ✅ | ✅ | ❌ 403 |
| 본인 배정 해제 | ✅ | ✅ | ❌ 403 |
| 타인에게 배정·재배정 | ❌ | ✅ | ❌ 403 |
| 타인 배정 해제 | ❌ | ✅ | ❌ 403 |
| `내 담당`·`미배정` 필터 | ✅ | ✅ | 미노출 |

배정 대상은 항상 `can_receive_orders = true`인 계정으로 서버에서 다시 검증한다.

이 매트릭스로 §25.5의 자리 비움 문제는 자동 해결된다 — `super_admin`이 재배정할 수 있다.

### 26.5 API (최종 3개)

| 메서드와 경로 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/order-assignees` | `can_receive_orders = true`인 배정 후보 조회 | `super_admin`만 |
| `POST /api/admin/order-assignments/batch` | 주문 ID 배열의 현재 담당자 일괄 조회 | `admin`·`super_admin` |
| `PUT /api/admin/order-assignments/[orderId]` | claim · release · assign · reassign | 동작별로 §26.4 검증 |

`PUT` 본문의 `assignee_profile_id`가 본인이 아니면 서버는 실행자가 `super_admin`인지 반드시 확인한다.

`admin`이 타인 ID를 실어 보내면 `403`으로 거부한다 — 클라이언트 UI 숨김에만 의존하지 않는다.

### 26.6 §25 대비 되돌린 항목

- 배정 대상 관리를 되살린다. 단 테이블이 아니라 `profiles.can_receive_orders` 컬럼이다.
- `GET /api/admin/order-assignees`를 되살린다. 단 `super_admin` 전용이다.
- 타인 배정·재배정·타인 해제를 되살린다. 단 `super_admin` 전용이다.

§25.3의 release(본인 해제)와 §25.4의 미배정 필터는 대표가 재확인했으므로 그대로 유지한다.

### 27.2 동시성 테스트 결과 (27건 전부 통과)

- 동시 claim 12건(두 담당자 교대) → **성공 정확히 1건**, 나머지 11건 `already_assigned` + 현재 담당자 반환.
- 이력도 정확히 1건만 기록됐다. 배정과 이력이 같은 트랜잭션에서 처리됨을 확인했다.
- 동시 해제 6건 → 실제 변경 1건, 나머지 5건 `version_conflict`.
- 잘못된 `version`으로 재배정 → `version_conflict` + 현재 버전 반환.
- `can_receive_orders = false` 계정에 배정 시도 → `assignee_not_allowed`로 거부.
- 존재하지 않는 주문 → `order_not_found`.
- 해제 시 행을 삭제하지 않고 `assignee_profile_id = null`, `assigned_at = null`로 유지.
- `anon` 키로 RPC 호출 차단, 신규 테이블 직접 조회 0행.
- 테스트 전후 `orders` 행의 md5 지문이 동일해 주문 원본이 변하지 않음을 확인했다.

테스트 대상은 2026-03-25자 취소 주문 1건이며 배정은 해제 상태로 되돌렸다.

감사 이력 3건이 그 주문에 테스트 흔적으로 남아 있다. 삭제는 승인 대상이라 보존했다.
